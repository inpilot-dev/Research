# 에이전트는 사용자의 자격증명을 읽지도 보유하지도 않는다

"어느 출처든 뚫고 간다"는 목표에서 가장 자연스러운 구현은 사용자의 키체인·브라우저 저장소에서 아이디와 비밀번호를 꺼내 로그인 폼을 채우는 것이다. 그렇게 하지 않는다. 웹 에이전트는 검색해 온 페이지에 심긴 지시문에 24~47% 확률로 넘어가고(research/15 §6, arXiv:2604.27202), 이 도구는 정의상 신뢰할 수 없는 페이지만 골라 읽는다. 자격증명을 쥔 채 그런 페이지를 읽는 에이전트는 한 번의 인젝션으로 계정을 잃는다. 완전한 인젝션 방어는 존재하지 않으므로 남는 방어는 최소권한 하나뿐이고, 최소권한의 구체적 형태가 "비밀번호를 아예 갖지 않는 것"이다. 실제로 이 사다리가 쓰는 aside CLI 는 `applePasswords` 라는 자격증명 접근 전역을 노출한다 — 쓸 수 있는데 쓰지 않기로 한 결정이다.

로그인 벽은 세 가지로만 처리한다. ① 사용자가 **이미 로그인해 둔** 브라우저 세션을 호스트별 옵트인으로 빌려 **읽기만** 한다 ② 사람에게 넘기고 무엇을 하면 되는지 알려준다 ③ 사용자가 직접 발급한 API 키를 쓴다. 셋 다 비밀번호가 에이전트 컨텍스트에 들어오지 않는다.

## Consequences

- CAPTCHA 를 풀지 않는다. `robots.txt` 의 Disallow 를 우회하지 않는다. 로그인 폼에 값을 넣는 코드 경로를 만들지 않는다.
- 이 경계는 산문이 아니라 테스트다. `tests/test_access_ladder.py` 의 `SacredList` 가 실행 코드(주석·독스트링 제외)에서 자격증명 API·폼 입력·CAPTCHA 처리 호출을 찾아내 실패시킨다.
- 사용자가 비밀번호를 알려주겠다고 해도 받지 않는다. 대신 세션 재사용을 제안한다.
- 뚫지 못하는 출처가 남는다. 그건 결함이 아니라 이 결정의 가격이며, "확인 불가"로 사유·시도 경로·방안과 함께 보고한다 (ADR 0003, [[0002]] 의 "어댑터 실패는 확인 불가").
